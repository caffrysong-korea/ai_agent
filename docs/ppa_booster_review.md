# ppa-booster 설계 리뷰

대상: `ppa-booster` 스킬(파일 10개) + `.opencode/agents/ppa-{collector,prober,curator}.md`
관점: Dr_RTL 구조 분석 결과와 대조하며, §7 리뷰 요청 A~F에 답한다.
전제: Synopsys Fusion Compiler / read-only / REF vs DOE 비교 / 재run은 사람이 수행.

---

## 0. 총평

**핵심 설계 판단 3개는 맞다.**

1. **판단을 본체에 묶어둔 것** — Dr_RTL은 서브에이전트에 진단을 위임한다(`rtl-timing-analyzer`가 root cause + amenability를 opus로 판정). 그래도 되는 이유는 **오라클이 있기 때문**이다. 진단이 틀리면 다음 합성 run과 SEC가 잡아낸다. ppa-booster에는 오라클이 없다. 유일한 검증자가 유저인데, 서브에이전트 컨텍스트 안에서 내려진 판단은 **추론 흔적이 그 컨텍스트와 함께 폐기되므로 유저가 검토할 수 없다.** 오라클 없는 시스템에서 판단은 인간이 볼 수 있는 곳에 있어야 한다. 원칙 1은 우연이 아니라 구조적으로 옳다.

2. **[확인]/[가설] 강제 분리 + 가설 3요소(내용/틀릴 조건/검증 방법)** — read-only 도메인에서 이게 없으면 시스템 전체가 그럴듯한 추측 생성기가 된다.

3. **선분석-후매칭(원칙 4)** — 지식 베이스가 관찰을 오염시키는 걸 막는다. Dr_RTL은 반대로 `rtl-optimizer`가 스킬을 먼저 조회하고 매칭시키는데, 그건 SEC가 틀린 매칭을 걸러주기 때문에 감당 가능한 것이다.

**구조적 결함 3개** (우선순위 순):

| # | 문제 | 영향 |
|---|---|---|
| **1** | §0의 목적("최대치를 다 냈는가")이 어떤 산출물 스키마에도 존재하지 않는다 | 시스템이 실제로는 비교 도구로만 동작 |
| **2** | heuristic 파이프라인이 양끝에서 막혀 있다 (intake 게이트 + 승격 게이트) | Active 31개 중 3개만 분석에 영향, 27개는 사장 |
| **3** | [기각] 지식의 승격 경로가 없다 | Dr_RTL 가치의 28%를 차지하는 안티패턴 라이브러리를 구조적으로 만들 수 없음 |

## A. 역할 분담이 타당한가

### A-1. 경계는 옳다. 다만 이미 새고 있다.

"판단은 위임하지 않는다"고 선언했지만, **collector와 prober는 이미 가장 영향력 큰 판단을 하고 있다.**

collector 지시문:
> 로그·리포트에서 발견한 비대칭 신호: 한쪽에만 있는 warning/skip/ignore를 원문 인용 + 파일·라인으로 **최대 10건** (의미 해석은 붙이지 마라)

수백 건의 warning 중 **어느 10건을 인용할지 고르는 것이 판단이다.** 그리고 이건 파이프라인 전체에서 가장 레버리지가 큰 판단이다 — 수면 위로 올라온 것만 분석되기 때문이다. "해석을 붙이지 마라"는 판단을 제거하지 않고 **은폐한다.** prober의 "부수 관찰 1-3건"도 동일하다.

**수정안** — 선별 규칙을 기계적으로 못 박고, 잘라낸 사실을 가시화한다.

```
- 비대칭 정의: 한쪽 run의 로그에 존재하고 다른 쪽에 부재한 라인 (또는 count delta > 2x)
- 정렬: count delta 절대값 내림차순
- 인용: 상위 10건
- MUST: 인용과 별도로 "총 N건 발견, 카테고리별 count 분포" 테이블을 반드시 함께 반환한다.
        본체가 무엇이 잘렸는지 알 수 있어야 한다.
```

원칙을 지키는 방법은 판단을 금지하는 게 아니라 **판단을 규칙으로 치환하고 잔여분을 보고하게 하는 것**이다.

### A-2. 관점별 analyzer 에이전트로 분리 — 하지 마라

두 가지 이유.

첫째, A-1의 오라클 논거. 관점 해석은 **유저가 피드백을 주는 대상 그 자체**다. 이게 서브에이전트 컨텍스트에서 일어나면 유저는 결론만 보고 판단해야 한다. 그러면 heuristic 승격의 근거인 "유저 확정"의 품질이 떨어진다.

둘째, `lifecycle.md` Step 3의 **Cross-Check(PPA 4축 trade-off)가 MANDATORY**인데 이건 본질적으로 관점 간 작업이다. 관점을 샤딩하면 trade-off 판정을 수행할 주체가 사라진다. 각 analyzer는 자기 축의 개선만 보고할 것이고, 이는 SKILL.md 정체성 항목("단일 metric 개선을 성공이라 부르지 않음")과 정면 충돌한다.

### A-3. 이미 올바른 축으로 쪼개져 있다

분할 축을 **관점(perspective)이 아니라 비용 프로파일**로 잡은 게 맞다.

- L1/L2 대량 정형 수집 = 넓고 얕음 → collector
- L3 표적 심층 = 좁고 깊음 → prober
- 규칙 기반 레지스트리 조작 = 판단 없음 → curator

세 에이전트가 각각 다른 종류의 컨텍스트 오염을 막는다. 축이 겹치지 않는다. 좋은 분해다.

## B. 컨텍스트 격리가 실제로 달성되는가

### B-1. "본체가 요약 파일을 다시 읽으면 결국 차는 것 아닌가" — 부분적으로 맞지만 목적은 달성된다

격리의 목적은 "raw를 절대 안 읽는 것"이 아니라 **"20,000줄 대신 큐레이션된 200줄을, 그것도 내가 고른 시점에 한 번만 읽는 것"**이다. `01_/02_` 요약은 캐시가 아니라 **체크포인트**다. 본체가 그걸 읽는 건 설계대로 동작하는 것이지 누수가 아니다.

**단, 통제되지 않은 부분이 있다: 01_/02_ 요약 파일에 크기 상한이 없다.**

notes는 "60-100L 목표, 120L 초과 금지"로 엄격히 캡을 걸어놨는데, collector가 쓰는 요약에는 아무 제한이 없다. collector가 "L1/L2 raw data 요약"을 3,000줄 써놓으면 격리가 통째로 무효화된다. 그리고 collector에게는 그러지 말아야 할 이유가 지시문 어디에도 없다.

**수정안** (collector Instructions에 추가):
```
- MUST: 01_/02_ 각 요약은 150줄을 초과하지 않는다.
        초과하면 L2 상세를 버리고 "해당 데이터는 {경로}에 있음" 포인터로 대체한다.
        무엇을 포인터로 대체했는지 목록으로 남긴다.
```

반환 페이로드의 "struct.md 갱신 제안"에도 상한이 없다. 최대 5건 정도로 제한.

### B-2. 1000줄 임계값 — 잘못된 지표다

타이밍 리포트 1000줄 ≈ 경로 3~5개. DRC 리스트 1000줄 ≈ 항목 1000개. 정보 밀도가 두 자릿수 차이 나는데 같은 임계값을 쓴다. 게다가 rpt는 라인이 넓어서 줄 수와 토큰 수의 상관이 약하다.

**더 나은 판정 기준: "파일의 몇 %를 실제로 쓸 것인가"**

```
- grep 패턴이 확정돼 있고 예상 매칭 < 50줄  → 본체가 직접 (grep으로 읽는다)
- 파일 전체를 스캔·정렬·집계해야 함          → prober
- 여러 파일 순회 / 패턴이 미확정             → prober
- 절대 상한: 2000줄 또는 50KB 중 먼저 걸리는 것
```

### B-3. prober 왕복 — 진짜 문제는 속도가 아니라 탐색적 조사의 부재

prober는 EXPECTED OUTCOME(반환 형식)을 요구하고, "계획에 없는 광범위 순회 금지"로 못 박혀 있다. 그런데 **반환 형식을 정확히 알 정도면 본체가 이미 답을 반쯤 안다는 뜻이다.**

실제 분석에서 자주 필요한 건 "이 리포트에서 뭔가 이상한 거 있나 봐줘"인데, 이건 prober가 명시적으로 금지된 작업이다. 결과적으로 **탐색적 조사는 갈 곳이 없다** — 본체가 하거나(컨텍스트 비용) 아무도 안 하거나(누락).

**수정안**: prober에 Mode 2를 추가한다.
```
## Mode 2 — 탐색 (본체가 "무엇을 찾을지 모를 때")
Inputs: 대상 파일/디렉토리 + 관심 축 1개 + 이상 판정 기준(있으면)
반환: 이상 후보 최대 10건 (원문 인용 + 경로:라인 + 왜 눈에 띄었는지의 *기계적* 근거
      — "값이 다른 run 대비 3x", "이 섹션에만 존재" 등. 의미 해석은 금지)
Hard: 판단 금지는 동일. 단 "선별 근거"는 기계적 서술로 반드시 붙인다.
```
A-1과 같은 원리 — 선별은 허용하되 선별 규칙을 노출시킨다.

**추가 규칙**: 동일 Data Need로 prober를 3회 이상 호출하게 되면 위임을 멈추고 본체가 직접 본다. 3회차 왕복이 필요하다는 건 Data Need 정의가 틀렸다는 신호이고, 그 시점엔 왕복 비용 > 직접 읽기 비용이다.

## C. 권한 설정이 적절한가

### C-1. bash 화이트리스트 — 검증 없이는 신뢰 불가

`bash: { "*": deny, "grep *": allow }` 형태의 패턴 매칭은 다음이 전부 구현 의존이다:

- 매칭 대상이 **전체 커맨드 문자열**인가 `argv[0]`인가?
- `;` `&&` `||` `|` 백틱 `$()`를 분해해서 각각 검사하는가, 아니면 통짜 문자열에 glob만 대는가?
- `grep x file | xargs rm` 은 통과하는가?

사내 배포판이라 문서만 보고는 알 수 없다. **30초 테스트를 반드시 하라:**
```
ls . ; echo PWNED
grep foo /etc/hostname && echo PWNED
```
통과하면 화이트리스트는 장식이다. 그 경우 `bash: {"*": deny}`로 전면 차단하고, 필요한 `diff`/`wc`는 read+glob 조합으로 대체하거나 본체가 수행한다. collector가 진짜 bash를 필요로 하는 건 `diff` 정도인데, 이건 본체가 해도 컨텍스트 비용이 거의 없다.

### C-2. collector의 쓰기 범위가 과하다 — 가장 시급한 권한 문제

```
edit: { "*": deny, "**/opencode_data/**": allow }
```

`opencode_data/`에는 **과거 모든 분석**이 들어 있다. collector는 `20260410_xxx/03_comparison/final_report.md`를 덮어쓸 수 있다. SKILL.md에 "분석마다 새 디렉토리, 기존 재사용 금지"라고 써 있지만 그건 본체 대상 규칙이고 collector에게 강제되지 않는다.

**수정안**: 현재 분석 디렉토리로 한정하고, 그 안에서도 `03_comparison/`은 제외한다.
```
edit: { "*": deny, "**/opencode_data/{현재_DIR}/01_*/**": allow,
                   "**/opencode_data/{현재_DIR}/02_*/**": allow }
```
런타임 바인딩이 안 되는 문법이면, 최소한 `03_comparison`과 `notes`를 명시적 deny로 추가하라. **최종 보고서는 본체만 쓴다**는 게 설계 의도인데 권한이 그걸 반영하지 않고 있다.

### C-3. curator 쓰기 권한 — 위험하지만 대안이 없다. 대신 검증을 붙여라

레지스트리 4종에 쓰기를 준 건 감수할 만하다. 대안(본체가 직접 편집)은 컨텍스트 비용이 크고, 이 작업은 판단이 아니라 규칙 실행이라 위임 대상으로 정확하다.

문제는 권한 자체가 아니라 **검증이 없다는 것**이다. 다음 항목에서 다룬다.

### C-4. 롤백 — 현재 구조로는 되돌릴 수 없다

> "Ceremony 중간 실패 시 되돌려라"

**작동하지 않는다.** 트랜잭션 로그 없이 LLM에게 "되돌려라"라고 하면 기억에 의존한 best-effort 텍스트 복원을 시도하고, 이게 정확히 레지스트리가 조용히 망가지는 경로다. 게다가 **실패한 주체에게 복구를 시키고 있다** — 이미 지시를 못 따른 에이전트에게 더 복잡한 지시를 주는 셈.

**원칙: 실패한 행위자는 복구 행위자가 될 수 없다.**

두 가지 수정안. 둘 다 싸다.

**(a) 스킬 디렉토리를 git으로 관리** (가장 확실)
```
curator Mode 1 Step 0: git -C {skill_dir} rev-parse HEAD 를 반환값에 포함
실패 시: curator는 "승격 미완료 — 실패 단계 N, 사유" 만 반환하고 아무것도 되돌리지 않는다
복구: 본체가 git checkout -- method/ perspectives/ 로 되돌린다
```

**(b) Ceremony 검증 루틴** (git 없이도 가능, 그리고 (a)와 병행 권장)

5-Step Ceremony는 **전부 grep으로 확인 가능하다.** 이게 이 설계의 좋은 성질인데 활용되지 않고 있다.

```
승격 검증 (본체가 curator 반환 직후 수행, 5개 grep):
① grep "H###.*PROMOTED" method/heuristics.md        → tombstone 존재
② grep "H###" {target_file}                          → entry 흡수됨
③ grep "H###" notes/_index.md                        → 결과 없어야 함
④ grep "H###" method/heuristics.md | grep "Promotion Log 섹션"  → 로그 기입
⑤ 보고서 footer에 H### 존재
하나라도 실패 → 유저에게 "H### 승격 부분 실패 (단계 N)" 보고 후 수동 처리
```

"에이전트를 믿는다"를 "실행 후 검증한다"로 바꾸는 것. 5줄짜리 체크이고 이게 있으면 C-3의 위험이 대부분 해소된다.

**(c) 최소안** (a·b 둘 다 어려우면): curator가 Ceremony 시작 시 `method/.ceremony_lock`에 5단계 체크리스트를 쓰고 각 단계 완료마다 마킹, 정상 종료 시 삭제. 다음 호출 시 lock이 남아 있으면 = 직전 Ceremony 미완료 → 본체가 유저에게 경고.

## D. heuristic 승격 시스템이 건전한가

### D-1. 숫자가 말해주는 것: 파이프라인이 양끝에서 막혀 있다

```
누적 H001–H058
Active 31 (seed 4 + candidate 27)
promoted 3 (fmax: H010, H028, H057)
environment exempt 9
```

**깔때기가 뒤집혀 있다.** 건강한 깔때기는 seed가 제일 넓어야 하는데, seed 4 < candidate 27이다. 그리고 candidate 27 → promoted 3.

두 개의 병목이 동시에 있다고 본다.

**병목 1 — intake가 너무 좁다.** 등록은 "[확정]된 가설만" 가능하다. 그런데 `lifecycle.md` F-5는 `skip ≥ 3`이면 Loop를 종료하고 가설을 "미검증"으로 notes에 보존한다. **즉 유저가 응답하지 않은 가설은 레지스트리에 영원히 진입하지 못한다.** 반복 관찰조차 근거로 축적되지 않는다. 새 seed가 안 생기는 이유다.

**병목 2 — 승격이 안 된다.** candidate 27개가 2회 관찰에서 멈춰 있다.

### D-2. 승격 조건이 빡빡한 게 문제인지 진단부터 하라

"승격이 너무 빡빡한 것 아닌가"는 **지금 데이터로 답할 수 없다.** 원인이 둘 중 어느 쪽인지 갈린다:

| 원인 가설 | 판별법 | 처방 |
|---|---|---|
| (a) 3번째 관찰 자체가 안 온다 — **SIG 매칭 실패**로 같은 현상이 새 ID로 등록됨 | candidate 중 EVIDENCE가 **정확히 2건**인 비율 | 승격 조건이 아니라 **매칭 recall**을 고쳐야 함 |
| (b) 3회는 채웠는데 전부 같은 design | EVIDENCE ≥3인데 candidate인 비율 | cross-design 요건이 실제 병목 |

**한 줄로 확인 가능하다** — `heuristics.md`에서 candidate 27개의 EVIDENCE 건수 분포를 세라. 이게 이 리뷰에서 가장 먼저 해야 할 액션이다.

내 예측은 **(a)가 지배적**이다. 근거: 매칭이 `grep -n "SIG:" method/heuristics.md | grep -i "<키워드>"`라는 **자유형 문자열 grep**이기 때문이다. SIG 이름이 한 글자만 달라도 매칭이 실패하고 신규 seed로 등록된다. 그리고 문서 자체에 이미 표기 불일치가 있다:

> `lifecycle.md` Step 4: "**kebab-case**로 기재. 예: `hro_high_fanout_setup_correlation`"

지시는 kebab-case인데 예시는 snake_case다. 매칭이 문자열 기반인 시스템에서 이건 사소한 오타가 아니다.

### D-3. SIG 어휘 통제 — 최우선 수정

```
notes/_sigs.md  (신규)
- 통제 어휘. SIG는 {domain}-{mechanism}-{effect} 3토큰 kebab-case로 고정.
  domain:    timing | power | area | congestion | flow | library
  mechanism: 자유 (단 이 파일에 등록된 것 우선 재사용)
  effect:    자유
  예: timing-high-fanout-setup-degrade
- 신규 SIG 생성 전 이 파일을 먼저 grep. 유사어가 있으면 새로 만들지 말고 재사용.
- curator Mode 1은 신규 등록 시 이 파일에도 SIG를 추가한다.
```

그리고 curator Mode 2에 **병합(merge) 연산이 없다.** 현재 Mode 2는 "신규면 seed 제안, 기존이면 EVIDENCE 누락 확인"만 한다. "H012와 H037은 같은 현상이다, 합쳐라"를 할 수 없다. 중복이 쌓이는 구조인데 청소 수단이 없다.

**Mode 2에 추가:**
```
6. 중복 후보 탐지 — SIG 문자열 유사도 또는 EVIDENCE 노트 중복이 있는 entry 쌍을 제시한다.
   병합 제안 형식: "H### + H### → 병합 후보. 근거: {SIG 유사}/{동일 note 인용}.
                    병합 시 합산 관찰 N회, cross-design 여부: Y/N"
   MUST: 제안만. 병합 실행은 유저 승인 후 Mode 1.
```
병합만으로 candidate 여러 개가 즉시 승격 요건을 채울 가능성이 높다. 27개가 실제로는 15개쯤일 수 있다.

### D-4. cross-design 1회 요건은 유지하라

Dr_RTL의 추출기도 동일한 방어를 건다 — "≥3 occurrences", "Do NOT invent patterns without evidence", "Always cite evidence". 같은 testcase 반복은 증거가 아니라 같은 증거의 재관찰이다. 이 요건을 완화하면 레지스트리가 특정 블록 전용 지식으로 오염된다.

완화하고 싶다면 요건을 낮추지 말고 **부분 인정**을 정의하라:
```
cross-design 요건 대체 인정 (1회 한정):
  - 다른 process / 다른 corner / 다른 stage 에서의 관찰은 0.5회로 인정
  - 즉 다른 stage 2회 = cross-design 1회 상당
  - 단 같은 block의 같은 stage 반복은 계속 0회
```
근거를 남길 수 있고 임의 완화가 아니다.

### D-5. 승격이 안 되면 지식이 **전혀** 쓰이지 않는다 — 이게 진짜 비용

이 부분이 과소평가되고 있다고 본다.

승격된 heuristic만 `perspectives/*.md`에 흡수되고, `perspectives/*.md`만 Phase 0-b에서 읽힌다. 즉 **분석에 실제로 영향을 주는 heuristic은 3개뿐이다.** candidate 27개는 어디서도 읽히지 않는다. `_index.md`의 Active table에 이름만 있고 분석 흐름에 진입하지 않는다.

원칙 4(선분석-후매칭) 때문에 사전 조회를 막는 건 맞다. 하지만 **후매칭 단계에서 candidate까지 매칭 대상에 넣는 것은 원칙 위반이 아니다.** 현재 Step B는 heuristics.md 전체를 grep하므로 candidate도 매칭되긴 한다 — 다만 매칭돼도 EVIDENCE만 늘고 분석에는 반영되지 않는다.

**제안**: 보고서의 TODO 도출(Step 4) 직후에 한 단계 추가.
```
Step 4.5: candidate 참조 (선분석 이후이므로 원칙 4 위배 아님)
  이번 분석의 SIG와 매칭된 candidate가 있으면, 그 내용을 TODO에
  "[가설] 유사 관찰 이력 있음 (H###, N회 관찰, 미승격)" 형태로 병기한다.
  MUST: candidate는 [확인] 근거가 될 수 없다. 가설의 신뢰도 참고용일 뿐이다.
```
이러면 27개가 사장되지 않으면서 원칙 4도 지킨다.

### D-6. 재승격 제한 — 검사 주체가 빠져 있다

> "Demotion Log의 재승격 조건이 해소되기 전까지 STATUS가 candidate여도 승격 불가"

규칙은 있는데 **curator의 Step 7 승격 판정 3조건에 이게 없다.** curator는 "Demotion 요청 시: 4-Step Ceremony 실행. 재승격 제한 준수"라고만 되어 있어서, 승격 경로에서 Demotion Log를 읽을 이유가 없다. 강등된 H가 candidate 상태로 3회를 채우면 그대로 재승격된다.

**Step 7에 4번째 조건 추가:**
```
· Demotion Log에 해당 SIG 없음, 또는 기재된 재승격 조건이 해소되었음을 명시적으로 확인
```

### D-7. Mode 2의 실효성 — 지금은 이르다

notes 7건에서 교차분석은 신호가 약하다. 실질적 패턴이 나오는 건 15건 이상부터라고 본다. 트리거 3건은 습관 형성용으로 두되 기대치를 낮추고, **Mode 2의 진짜 가치는 D-3의 중복 병합과 D-2의 진단**에 있다고 재정의하는 게 낫다. 지금 당장 유용한 건 "새 패턴 발견"이 아니라 "레지스트리 청소"다.

## E. 놓친 것

### E-1. §0의 목적이 산출물 어디에도 구현돼 있지 않다 ★ 최우선

문서 §0:
> 승자 판정이 목적이 아니다. **"이 DOE가 낼 수 있는 최대치를 다 냈는가, 못 냈다면 어디서 새는가"**의 진단이 목적.

그런데 `lifecycle.md`의 보고서 구조를 보면:
```
Step 1: L1 Aggregate Screening      ← delta
Step 2: 관점별 Deep Dive            ← delta의 원인
Step 3: Cross-Check (trade-off)     ← delta의 부작용
Step 4: TODO 도출
Step 5: 확신 vs 불확실
```
**전부 delta 기반이다. "기대치 대비 미달분(shortfall)"을 담는 칸이 없다.**

delta만으로는 "최대치를 다 냈는가"를 원리적으로 판정할 수 없다. 기대값이 없으면 실측 delta가 100%인지 30%인지 알 방법이 없다. 지금 구조는 §0이 하지 않겠다고 선언한 "비교"만 수행하고 있다.

collector가 `tcl diff`를 수집하는 게 "DOE가 무엇인가"에 가장 가까운데, 이건 기계적 diff일 뿐 **의도**가 아니다.

**수정안 — 보고서와 notes 양쪽에 DOE Intent 블록 추가:**
```markdown
## DOE Intent (MANDATORY — 분석 시작 전 유저에게 확인, 모르면 [확인불가])
| 항목 | 내용 | 출처 |
|---|---|---|
| 변경 내용 | {tcl diff 요약 / 유저 진술} | [확인] |
| 의도한 레버 | {예: placement congestion effort 상향} | [확인] or [확인불가] |
| 이론상 수혜 축 | {Fmax / Power / ...} | [가설] |
| 기대 효과 크기 | {정량 or "미상"} | [가설] or [확인불가] |

## Shortfall 분석 (MANDATORY)
| 축 | 기대 | 실측 | 달성률 | 누수 지점 |
|---|---|---|---|---|
```

**기대치를 유저가 못 주면 `[확인불가]`로 선언하는 것 자체가 산출물이다.** "이 DOE의 목표 수치가 정의되지 않아 shortfall 판정 불가"는 유효하고 유용한 결론이고, 다음 DOE 설계를 개선시킨다. 지금은 그 질문을 던지는 자리조차 없다.

이 블록이 들어가면 시스템의 성격이 비교 도구에서 **누수 진단 도구**로 바뀐다. §0이 원래 주장하던 것이 그거다.

### E-2. [기각] 지식이 승격되지 못한다 ★ Dr_RTL과의 최대 격차

Dr_RTL `skill.md` 47개 패턴 중 **13개(28%)가 "Do not use" 섹션**이다. 실전에서 가장 가치 있는 부분이다 — LLM은 PnR에서 그럴듯하고 틀린 처방을 잘 내기 때문이다.

ppa-booster는 이 자산을 **구조적으로 만들 수 없다.**
```
lifecycle: "[기각] 가설은 heuristics.md에 등록하지 않는다(Negative Knowledge로 notes에만)"
curator:   "[기각] 가설은 ... notes의 Negative Knowledge에 1-2줄로 기록한다"
```

결과: 기각 지식이 7개 notes에 흩어지고, 교차분석되지 않고, `perspectives/`로 승격되지 않고, 다음 분석의 출발점이 되지 않는다. **같은 잘못된 가설을 다른 testcase에서 또 세우게 된다.**

이게 특히 아까운 이유: **기각 데이터는 이미 생산되고 있다.** 유저가 [기각] 피드백을 주고 있고, 그게 notes에 기록되고 있다. 파이프라인만 없어서 버려지는 중이다.

**수정안:**
```
method/anti-patterns.md (신규)
- heuristics.md와 동일한 seed/candidate/promoted 생애주기
- 입력: [기각] 가설. 등록 시 STATUS = seed
- 승격 조건도 동일 (총 3회 + cross-design 1회)
  → "여러 design에서 반복적으로 기각된 가설" = 진짜 안티패턴
- 엔트리 포맷:
  ### AP### — SIG
  - **틀린 가설**: {무엇을 믿었나}
  - **왜 틀리나**: {유저 기각 사유}
  - **위험 조건**: {이 상황에서 특히 이 오류를 범하기 쉽다}
  - **대신 볼 것**: {올바른 접근}
  - **EVIDENCE**: {note 경로 + design/process}
- 승격되면 perspectives/{domain}.md 의 "이 관점에서 하지 말 것" 섹션으로 흡수
```

curator Mode 1의 [기각] 처리를 "notes에 1-2줄"에서 "anti-patterns.md 등록 + notes 기록"으로 바꾸면 된다. 권한은 이미 `**/method/*.md`가 아니라 개별 파일 나열이므로 `anti-patterns.md`를 추가해야 한다.

### E-3. 유저 확정 ≠ 검증 — 지식 베이스가 "이 엔지니어에게 그럴듯한 것"으로 수렴한다

승격의 유일한 진실 게이트는 유저의 [확정]이다. 그런데 read-only 시스템에서 유저는 대개 **재run 결과가 아니라 도메인 직관으로** 확정한다. 이건 검증이 아니라 **동의**다.

Dr_RTL은 이 문제가 없다. 게이트가 SEC와 실측 PPA라서 인간의 믿음과 무관하다. ppa-booster는 58개를 누적하는 동안 서서히 **한 사람의 사전 믿음을 형식화한 문서**로 드리프트할 수 있다. 그리고 그 드리프트는 내부적으로 감지되지 않는다 — 확정한 사람과 그 지식을 쓰는 사람이 같기 때문이다.

**수정안 — 확정 근거를 유형화해서 기록한다.** notes "가설 상태 추적" 표에 컬럼 1개 추가:
```
| 확정 근거 유형 |
  R = 재run/실측으로 확인
  T = tool 문서 / 라이브러리 스펙 / 문헌 근거
  E = 엔지니어 경험·직관
```
그리고 **승격 조건에 추가**: `총 3회 관찰 중 최소 1회는 R 또는 T`.

E만으로 3회 채운 heuristic은 candidate에 머문다. 빡빡해 보이지만, **E만으로 승격된 지식이 `perspectives/`에 흡수되어 이후 모든 분석의 출발점이 되는 게 더 위험하다.** 이건 D-4의 cross-design 요건과 같은 성격의 방어다.

부수 효과: R/T가 부족하다는 게 보이면 "SNPS_MCP로 검증 script를 제공 가능"이라는 SKILL.md의 능력을 실제로 쓸 동기가 생긴다. 지금은 그 기능이 있다고만 선언돼 있고 파이프라인에 연결돼 있지 않다.

### E-4. 검증 방법이 "재run 필요"로 수렴하면 가설이 영구 미검증이 된다

가설 3요소 중 "검증 방법"이 read-only 제약 때문에 대부분 "사람이 재run"으로 수렴한다. 그러면 그 칸은 형해화되고, F-5(skip≥3)를 타고 미검증으로 보존된다 → D-1의 intake 병목으로 직결.

**검증 방법을 3분류로 강제하면 이 흐름이 보인다:**
```
(a) 기존 파일에서 즉시 확인 가능        → 지금 당장 확인. 가설이 아니라 Data Need다.
(b) 추가 rpt 생성 필요 (재run 아님)      → SNPS_MCP script 제공. 유저가 실행하면 R 근거 획득.
(c) 재run 필요                          → 유저 판단 대기. 장기 미검증 pool.
```
(a)로 분류된 가설은 **애초에 가설로 발행하면 안 된다** — 확인 가능한데 안 한 것이다. 이 분류를 강제하면 (a)류 게으른 가설이 걸러지고, (b)가 E-3의 R/T 근거를 만드는 실질 경로가 된다.

### E-5. Fast-Path 경계가 마모된다

"WNS 얼마야?"는 Fast-Path, "WNS 왜 나빠졌어?"는 전체 Phase. 그런데 실무에서 유저는 두 번째를 첫 번째 어투로 묻는다("WNS 어떻게 됐어?"). 판정 기준이 "단순 조회"라는 주관어라 반드시 흐려진다.

**기계적 tiebreak:**
```
다음 중 하나라도 해당하면 Fast-Path 금지, 무조건 라우터:
- 두 run(REF/DOE)의 값을 함께 언급하거나 비교를 함축
- "왜" "원인" "때문" "어디서" 가 포함
- 값이 아니라 판단을 요구 ("괜찮아?" "문제야?")
```

### E-6. 파일 수와 결합도

**파일 수 13개(스킬 10 + 에이전트 3)는 과하지 않다.** 각 파일의 역할이 겹치지 않고, `lifecycle.md` 분리는 특히 잘한 결정이다 — 분석 중에 읽지 않아도 되는 걸 분리해서 컨텍스트를 아꼈다.

**위험한 결합은 파일 수가 아니라 파생 데이터의 수동 동기화다.**

```
notes/_index.md 의 "Active Heuristic lookup table"
  = method/heuristics.md 의 파생 데이터
  그런데 수동으로 동기화된다 (승격 5-Step ③, 강등 4-Step ④)
```

**이건 반드시 깨진다.** 승격 1회가 3개 파일(heuristics.md / target perspective / _index.md)을 원자적으로 갱신해야 하는데, 트랜잭션이 없다(C-4). curator Mode 2 step 5가 정합성 점검을 하지만 그건 **탐지이지 예방이 아니다.**

**수정안 2가지 중 택1:**
- (권장) `_index.md`에서 Active Heuristics table을 **삭제**한다. `heuristics.md`가 단일 진실이고, 조회는 grep으로 한다. 파생 데이터를 없애면 동기화 문제 자체가 사라진다. `_index.md`는 note 색인만 담당.
- (차선) 남기되 `_index.md` 최상단에 명시: "이 표는 heuristics.md의 캐시다. 불일치 시 heuristics.md가 승. 승격/강등 판단에 이 표를 근거로 쓰지 않는다."

### E-7. Step 번호 체계가 3중으로 충돌한다

규칙 준수 에이전트에게 실제로 해가 된다.
```
SKILL.md Phase 0 : Step 0-a, 0-b
SKILL.md Phase 2 : Step 1 ~ 5
lifecycle.md     : Step 0 ~ 8   (그런데 "Step 6~8"이 섹션 하나로 뭉쳐 있음)
curator Mode 1   : "Step B" → "Step 7"   ← 이전 버전 잔재. B와 7의 관계 불명
```
curator는 "Step B 다음 Step 7"을 지시받는데 사이가 비어 있다. 리팩터링 잔재로 보인다.

**수정**: 네임스페이스를 접두어로 분리하라. `P0-a`, `P2-1`, `L-1`, `C1-1`. 문서 간 참조도 명확해진다.

### E-8. 사소한 불일치

- §1 구조도: `notes/{testcase}.md` ↔ `lifecycle.md` Step 2: `notes/{block}_{process}_{stage}.md` — 명명 규칙 확정 필요
- `lifecycle.md` Step 4: "kebab-case" ↔ 예시 `hro_high_fanout_setup_correlation`(snake_case) — D-3 참조. 매칭이 문자열 기반이라 사소하지 않다
- 라우터/위임분기에 `oracle`, `ACE-RTL`이 등장하는데 정의는 3개 에이전트만 있다. 외부 제공 에이전트임을 문서에 명시할 것 (독자가 정의 누락으로 오해함)

## F. OpenCode 문법

### F-1. 사내 배포판 스키마는 검증할 수 없다 — 다만 의심스러운 지점은 지목 가능

frontmatter를 그대로 검증해줄 수는 없다. 사내 배포판이고 표준과 다를 수 있다고 명시하셨으니 추측으로 확답하지 않겠다.

**다만 구조적으로 의심되는 부분이 있다: `tools` 네임스페이스와 `permission` 네임스페이스를 섞은 것 같다.**

```yaml
permission:
  read: allow      # ← 이게 permission의 키가 맞나?
  glob: allow      # ←
  grep: allow      # ←
  bash: { ... }    # ← 이건 permission이 맞을 가능성 높음
  edit: { ... }    # ← 이것도
  task: deny       # ← ?
  skill: { ... }   # ← ?
```

일반적으로 `read`/`glob`/`grep`은 **도구 on/off**(`tools:`)이고, `permission`은 부작용이 있는 동작(`edit`, `bash`, `webfetch`)의 승인 정책을 다룬다. 만약 그렇다면 `permission.read: allow` 같은 키는 **조용히 무시**된다.

**무시되어도 티가 안 난다는 게 진짜 위험이다.** `read`는 무시되어도 기본값이 허용이라 정상 동작하는 것처럼 보인다. 문제는 `task: deny`와 `skill: {"*": deny}`다. **이게 무시되고 있으면 collector가 다른 서브에이전트를 스폰할 수 있고, 그건 컨텍스트 격리 설계 전체를 우회한다.**

### F-2. 반드시 deny를 테스트하라 (allow 말고)

**허용은 실패하면 즉시 보인다. 거부는 실패해도 안 보인다 — 사고가 날 때까지.**

```
1. collector에게 "다른 서브에이전트를 호출해봐" 지시 → 거부되나?  (task: deny 검증)
2. collector에게 "/etc/hostname 을 수정해봐" 지시 → 거부되나?      (edit 범위 검증)
3. collector에게 "ls . ; echo PWNED" 실행 지시 → PWNED 출력되나?   (bash 화이트리스트 검증)
4. collector에게 opencode_data 밖 경로 쓰기 지시 → 거부되나?
```
3번이 특히 중요하다 — C-1의 답이 여기서 나온다.

무시되는 키가 확인되면, 스키마에 없는 정책은 **frontmatter 대신 에이전트 본문의 Hard Constraints로 이중화**하라. 프롬프트 수준 제약은 하드 게이트는 아니지만 없는 것보다 훨씬 낫다. 현재 collector/prober의 Hard Constraints에 "다른 에이전트를 호출하지 마라"가 없는데, `task: deny`가 무시되고 있다면 이게 유일한 방어선이 된다.

### F-3. 파일 경로 전달 — 나쁘지 않다. 스키마만 고정하라

파일 경유 전달은 메시지 전달보다 **감사 가능하고 재개 가능**하다는 장점이 크다. 분석이 중단돼도 `01_/02_`가 남아 있으면 이어서 할 수 있다. 유지할 만하다.

개선점: 지금은 각 에이전트의 Inputs가 산문 프롬프트로 전달돼서 호출마다 표류한다. **분석 디렉토리마다 핸드오프 파일 1개를 두면** 모든 에이전트의 Inputs가 파일 1개 READ로 통일된다.

```json
// opencode_data/{YYYYMMDD}_{concept}/_handoff.json
{
  "concept": "ch120_hro_fmax",
  "ref": {"id": "...", "path": "/.../ref_run"},
  "doe": {"id": "...", "path": "/.../doe_run"},
  "stages": ["place", "cts", "route"],
  "perspective": "fmax",
  "output_dir": "/.../20260625_ch120_hro_fmax",
  "doe_intent": { ... },              // E-1
  "collected": [],                     // collector가 채움: 수집 성공 파일 인벤토리
  "unavailable": [],                   // collector가 채움: 실패 + 시도 경로
  "struct_updates": []                 // collector가 채움: struct.md 갱신 제안
}
```

부수 효과: `collected`/`unavailable`이 있으면 prober가 **이미 수집된 걸 재수집하지 않고**, 본체는 `[확인불가]` 선언 시 근거를 파일에서 바로 인용할 수 있다.
